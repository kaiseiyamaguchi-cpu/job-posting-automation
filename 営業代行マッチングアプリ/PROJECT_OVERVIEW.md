## 🎯 プロジェクトの背景

### ビジネス課題
鬼ニカナ社（設立1年目）は、営業代行と企業のマッチング業務を**手動で行っており、業務効率化が急務**。

現在の課題：
1. マッチングプロセスが手動で時間がかかる
2. 営業代行と企業間のコミュニケーションが煩雑
3. 案件状況の可視化ができていない
4. スケーラビリティがない

### ビジネスモデル
- **社内効率化ツール**（一般公開ではなくクローズド運用）
- 手数料型ではなく、業務効率化が主目的
- 将来的な機能拡張を見据えた設計

### なぜBubbleか
- **予算制約**: 100-150万円で実現可能
- **開発速度**: 2-4日で完成可能
- **保守性**: コード不要で変更が容易
- **将来性**: Flutter Flowへの移行でコード化が可能
- モバイルアプリ化は将来検討

## 🏗️ アプリ概要

### 一言で説明
> 営業代行を探す企業と、営業代行パートナーをつなぐマッチングプラットフォーム

### ユーザー種別
1. **企業（サービス利用者）**
   - 営業代行を検索・閲覧
   - メッセージでやり取り
   - 日程調整申請

2. **営業代行（サービス提供者）**
   - プロフィール登録
   - 企業とメッセージでやり取り
   - 日程調整の対応

3. **管理者（運営側）**
   - ダッシュボードで統計情報確認
   - 企業・営業代行情報の閲覧
   - ユーザー認証管理
   - 書類確認・本人確認
   - ユーザー削除

### コアバリュー
- シンプルで使いやすい
- メッセージから日程調整までシームレス
- リアルタイムなコミュニケーション
- 管理者による安全な運営管理

## 📊 データモデル

### ER図（簡易版）

```
users (ユーザー)
  ├─ id (unique id, PK)
  ├─ email (text)
  ├─ user_type (option: 'company' | 'sales_agency' | 'admin')
  ├─ is_verified (yes/no)
  ├─ verification_status (option: 'pending' | 'approved' | 'rejected')
  └─ created_date (date)

companies (企業)
  ├─ id (unique id, PK)
  ├─ user (relationship → users)
  ├─ company_name (text)
  ├─ industry (text)
  ├─ area (text)
  ├─ request_detail (text)
  ├─ contact_name (text)
  ├─ phone (text)
  ├─ document (file) ← 書類アップロード
  └─ verified_by (relationship → users/admin) ← 承認者

sales_agencies (営業代行)
  ├─ id (unique id, PK)
  ├─ user (relationship → users)
  ├─ company_name (text)
  ├─ contact_name (text)
  ├─ phone (text)
  ├─ specialties (list of texts)
  ├─ areas (list of texts)
  ├─ description (text)
  ├─ document (file) ← 書類アップロード
  └─ verified_by (relationship → users/admin)

message_threads (メッセージスレッド)
  ├─ id (unique id, PK)
  ├─ company (relationship → users)
  ├─ sales_agency (relationship → users)
  ├─ last_message_text (text)
  ├─ last_message_sender (relationship → users)
  ├─ last_message_at (date)
  ├─ company_unread_count (number)
  ├─ sales_agency_unread_count (number)
  └─ created_date (date)

messages (メッセージ)
  ├─ id (unique id, PK)
  ├─ thread (relationship → message_threads)
  ├─ sender (relationship → users)
  ├─ text (text)
  ├─ is_read (yes/no)
  └─ created_date (date)

schedule_requests (日程調整リクエスト) ← 追加
  ├─ id (unique id, PK)
  ├─ thread (relationship → message_threads)
  ├─ requested_by (relationship → users)
  ├─ requested_to (relationship → users)
  ├─ proposed_dates (list of dates) ← 候補日時
  ├─ confirmed_date (date) ← 確定日時
  ├─ calendar_event_id (text) ← 外部カレンダーID（API連携後）
  ├─ meeting_url (text) ← 会議URLメモ（手動入力）
  ├─ status (option: 'pending' | 'confirmed' | 'cancelled')
  ├─ notes (text)
  └─ created_date (date)
```

## 🔐 セキュリティ方針

### 認証・認可
- Supabase Authenticationによるセキュアな認証
- JWTトークンによるセッション管理
- Row Level Security (RLS) によるデータアクセス制御

### データ保護
- 環境変数による機密情報管理
- `.env.local` をGitに含めない
- パスワードのハッシュ化（Supabase自動）

### セキュリティレベル
- **中程度**（予算制約内）
- メール認証（二段階認証）
- XSS対策（React自動エスケープ）
- CSRF対策（Next.js標準）

### 禁止事項
- パスワードのログ出力
- APIキーのハードコード
- 認証なしでのデータアクセス
